# 推理延迟随运行增长的定位（2026-09-24）

## 方法

读取当前仿真一张 JPEG，冻结图像与指令，在服务器本机直接连接 `127.0.0.1:8050`。使用独立测试会话，连续顺序请求 80 次（无请求并发），随后只清空这个测试会话的历史再请求 5 次。不经过浏览器、SSH 转发或 MPC，不向小车发送命令。测试结束断开连接。

服务器：单个 lightnav-serve 进程，vllm_local 后端；CUDA_VISIBLE_DEVICES=1，物理 GPU 为 NVIDIA RTX A6000；启动命令未指定量化，代码默认 bf16。所有记录的 batch_size 为 1。

## 实测

| --- | ---: | ---: | ---: | ---: |
| 1 | 379 | 277 | 77 | 2.4 |

| 40 | 797 | 708 | 62 | 2.6 |
| 60 | 898 | 784 | 83 | 2.6 |
| 80 | 1019 | 911 | 78 | 2.6 |
| 清空历史后第 1 次 | 477 | 384 | 70 | 2.6 |

`vit_ms` 在服务层表示整个视觉阶段，包括处理器准备等，不能和其子项相加。第 80 次视觉缓存命中 25 个 tubelet、未命中 1 个，缓存没有被关闭。原始逐请求结果见 `results.json`，复现脚本见 `probe.py`。

## 机制与结论

checkpoint 的 eval_config.json 开启 SlowFast 分层历史采样，`policies.py` 在该模式下保存整段 episode；`samples.py` 根据已经收到的帧数量构建历史输入。虽然 JPEG 完全相同，不同时间位置依然是独立历史帧。

按当前配置计算，输入采样帧数（含对齐填充）随第 1/20/40/60/80 次请求依次为 2/20/38/44/52；约 120 帧历史后达到 82 帧的采样规模。完整历史缓冲区仍然增长，但不能将其等同于每次把全部历史送入模型，也不能据此宣称推理耗时必然无限增长。

增长主要来自语言模型处理更长的视觉上下文；视觉缓存命中只减少历史图像的视觉编码开销，不会消除语言模型处理上下文的开销。清空测试历史后，延迟明显下降，支持历史上下文增长是主要机制。该实验没有分别计时 LLM prefill/decode，也未控制生成 token 数，因此无法将 LLM 阶段耗时全部归到单一内核。

本机无 SSH 的测试同样复现 379→1019 ms，所以 SSH 不是这次逐步增长的必要原因；没有出现队列持续积压。原 MuJoCo 的图像等待缓存可能额外增加采图到执行的延迟，但并非本实验往返耗时增长的原因。
